# Phase 7 主机端 C 覆盖率报告

日期：2026-09-12（Asia/Shanghai）。

## 实测结果

本轮直接编译运行五个固件 C 源文件，通过 857 次断言检查（包含临界区进入/退出
平衡检查）。原有 Python 测试加上覆盖率解析器检查，共 20 项测试通过。

| 固件模块 | 命中/可执行行 | 行覆盖率 | 命中/分支结果 | 分支覆盖率 |
|---|---:|---:|---:|---:|
| vehicle_can.c | 56/56 | 100% | 32/32 | 100% |
| vehicle_state.c | 66/66 | 100% | 29/30 | 96.67% |
| dtc_manager.c | 116/116 | 100% | 52/56 | 92.86% |
| uds_server.c | 311/311 | 100% | 156/162 | 96.30% |
| pid.c | 30/30 | 100% | 18/18 | 100% |
| 合计 | 579/579 | 100% | 287/298 | 96.31% |

机器生成的原始结果：[coverage/latest.md](coverage/latest.md)；文件摘要、未命中
分支和统计：[coverage/latest.json](coverage/latest.json)。同目录 `.gcov` 文件可查看
每行执行次数和各分支次数。`latest-status.json` 表示最近一次运行是否完成并通过。
每次运行先将报告标记为进行中，再由成功完成的测试生成结果，避免旧 PASS 冒充本次结果。

这些百分比的分母仅包含表中五个模块。GCC 的行覆盖率表示该可执行源码行至少执行过
一次；一行包含条件和提前返回时，行命中并不表示该行所有语句或条件均已走到。
因此同时给出分支覆盖率，不能将 100% 行覆盖率表述成“全项目所有语句、分支均通过”。

## 测试如何运行

入口 `tools/run_host_coverage.py` 使用本机 MinGW GCC/gcov 8.1.0，编译参数为
`-O0 -g --coverage -Wall -Wextra -Werror`。每次在新的临时目录编译，避免累积旧
计数；源文件原样复制用于兼容 MinGW 的 Windows 中文路径，并记录 SHA256。
测试代码和替身实现不计入覆盖率分母；五个业务源文件未为测试修改。

替身仅位于 `tests/host/stubs`，不加入 Keil 工程：

- FreeRTOS 临界区改为计数检查，时钟由测试控制。
- 日志输出替换为空实现；传感器快照固定为 3300 mV，故障注入掩码为 0x12。
- SCB 向量地址、复位请求和 SRAM Boot 请求标志改为普通主机变量。
- UDS 仍调用真实 `vehicle_state.c` 和 `dtc_manager.c`，检查模块间交互。

测试通过公共函数调用实际固件实现，不把 Python 版本算法的执行次数算作 C 覆盖率。
主机上的整数 ABI、调度、内存布局和外设行为与 ARM 不同，所以本结果只验证业务逻辑。

## 验证场景

| 范围 | 主要断言 |
|---|---|
| CAN/CRC8 | 标准检查值 0x4B；空指针、错误长度、错误 CRC、保留位和档位；Alive 15→0 回绕、重复/失步拒收和恢复；拒收不更新目标；正负速度字节布局 |
| 状态机 | DRIVE 进入条件、超时 SAFE_STOP、致命故障优先级、故障解除、重复状态不增加转移次数 |
| DTC | 第 3 次失败确认、第 10 次正常恢复；Freeze Frame 的时间和命令；历史 DTC 保留；清除条件；恢复记录；发生次数 255 饱和 |
| PID | 空指针、正负限幅、积分抗饱和、微分与 dt=0、正负四舍五入、Reset |
| UDS | 长度/服务/子功能 NRC、DRIVE 下拒绝清除和编程；会话、Tester Present、S3 边界和 32 位时间回绕；DID、VIN 多帧重组、9 个 DTC 应答、FC 超时 |
| UDS 异步/队列 | 0x78→最终应答、重复例程 0x21；确认发送之后再延迟 50 ms 复位；抑制响应复位；编程请求标志；队列满时不触发未入队的复位；最终例程响应重试 |

队列满后的 ISO-TP 连续帧测试验证：入队失败保留偏移，后续再次收到 CTS 时从未发送
帧继续。该测试不证明完整 ISO-TP 流控合规性；STmin、BlockSize 等行为不在本次承诺范围。

## 11 个未覆盖分支结果

以下依据当前源码调用关系分析，全部保留在 298 个分支结果的分母中，没有屏蔽：

| 位置 | 数量 | 当前测试未能触发的原因 |
|---|---:|---|
| vehicle_state.c:134 | 1 | 公开状态转移在进入 DRIVE 前排除故障；无法通过正常 API 形成 DRIVE 且 fault_flags 非零 |
| dtc_manager.c:29 | 1 | 私有映射函数只由初始化的有效索引循环调用 |
| dtc_manager.c:113 | 1 | pass_count 达阈值同次调用即清除 TEST_FAILED，下次不会进入此计数分支 |
| dtc_manager.c:129、130 | 2 | occurrence/freeze 的首次变化伴随 status 变化，前面的短路条件已成立 |
| uds_server.c:112 | 2 | 私有单帧发送函数的现有调用点均提供有效数组和至多 7 字节 |
| uds_server.c:134 | 3 | 私有响应函数的现有调用点均提供非空、非零、范围内响应 |
| uds_server.c:203 | 1 | 使用固定有效 DTC 索引和非空输出地址，真实 DtcManager_GetRecord 不会失败 |

该分析不是形式化不可达证明。以后接口、并发约束或调用点改变时，需要重新评审这些分支。

## 复现与门槛

在项目根目录运行：

```powershell
D:\ProgramData\anaconda3\python.exe .\tools\run_host_coverage.py
D:\ProgramData\anaconda3\python.exe -m pytest -q
```

默认自动查找 gcc，也可传 `--gcc` 和匹配版本的 `--gcov`。无需额外 Python 包运行
C 覆盖率工具。编译失败、C 断言失败、缺失计数或总体行覆盖率低于 90%、分支低于 80%
均返回非零退出码；这是本项目初始门槛，不是行业认证标准。
